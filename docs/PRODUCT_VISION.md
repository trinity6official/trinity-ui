# Product Vision

## Purpose

Trinity6 should help people understand and accomplish complex digital work through an interactive visual environment and Trinity intelligence.

The product progression is:

**Explore → Learn → Build → Create → Run**

## Explore

Users should be able to understand meaningful systems visually: people, devices, networks, servers, applications, databases, cloud services, controls, data flows, physical access, and business processes.

The first experience begins with a **full-company view** rather than an isolated room or dashboard.

The user should feel that the company exists as a navigable digital environment.

## Learn

Learning should happen through guided interaction, spatial explanations, simulations, scenarios, and challenges rather than passive feature pages.

Initial domains include:

- cybersecurity;
- networking;
- cloud;
- AI;
- software;
- data;
- privacy;
- GRC;
- IT infrastructure.

The flagship guided experience remains:

**How a company gets hacked — and how to protect it.**

The attack path should eventually be represented spatially through the real infrastructure inside the company world.

## Build

Trinity should help users turn goals into real projects.

Future flows may include:

- start an AI business;
- launch an application or SaaS product;
- create a digital product;
- build a creator workflow;
- operate an AI-enabled business.

The system should model milestones, evidence, artifacts, and actions instead of arbitrary gamification.

## Create

A future Creator Studio should allow educators and creators to author interactive experiences without programming.

Creator experiences should eventually support:

- templates;
- scenes and entities;
- relationships;
- narration and guided steps;
- simulations;
- quizzes/challenges;
- preview;
- publishing;
- sharing/embedding;
- analytics;
- monetization.

## Run

For advanced users and organizations, Trinity can evolve from guidance into an operational assistant using explicit permissions, integrations, workflows, analytics, and automation.

The long-term organizational view may connect authorized real infrastructure to the same visual interaction model.

## First world: the Trinity6 company

The first public world is one premium multi-floor company environment.

The landing experience should immediately communicate:

> This is a complete digital company that I can explore.

The initial company contains recognizable areas and systems such as:

- reception / secure entrance;
- employee workspaces;
- network infrastructure;
- firewall/security boundary;
- server room;
- database/application systems;
- cloud connections;
- CCTV and physical access;
- data and network paths.

The visual model is not a dashboard and not a collection of floating labels.

It is a spatial environment.

## Interaction model

The first interaction sequence is:

```text
Full company view
      ↓
Explore / inspect building zones
      ↓
Select access card
      ↓
Touch entrance / reader
      ↓
Identity verified
      ↓
Doors open
      ↓
Camera enters lobby
      ↓
Navigate deeper
```

Future drill-down:

```text
Company
  ↓
Floor
  ↓
Room
  ↓
Rack / equipment
  ↓
Device
  ↓
Application / data / risks / controls / dependencies
```

Desktop can use hover and pointer focus.

Mobile is first-class and uses touch-first behavior such as tap-to-select, tap-to-activate, larger interaction targets, and mobile-specific camera framing.

## Trinity

Trinity is the intelligence layer, not a generic floating chatbot.

Trinity should eventually be able to:

- focus an entity;
- move the camera to a meaningful location;
- highlight relationships;
- explain a room or device;
- start a guided experience;
- follow an attack path;
- compare states;
- explain dependencies;
- answer questions about the current world;
- help users build new experiences or projects.

The AI implementation remains independently owned by `trinity-ai`.

## Visual quality target

The production world should feel like a premium architectural visualization / digital twin:

- complete multi-floor building;
- readable room interiors;
- realistic glass, metal, concrete, lighting, vegetation, furniture, and infrastructure;
- warm interior lighting contrasted with restrained cyan digital accents;
- visible server racks and networking equipment;
- visible physical infrastructure where meaningful;
- cinematic but usable camera movement;
- minimal, elegant UI overlays.

The digital layer should enhance a believable building rather than replace it.

## Visual implementation principle

Three.js is the runtime and interaction engine.

Production architectural quality should come from professionally authored 3D assets, primarily standard `.glb/.gltf` models produced through Blender or another compatible authoring pipeline.

The reference-quality visual target must not be implemented as a static screenshot with invisible interaction overlays.

The image/reference is art direction; the production world must remain spatial and interactive.

## Business model hypothesis

Start with a useful free experience to maximize learning, exploration, sharing, and creator adoption.

Potential future professional value includes:

- advanced creation;
- private projects;
- collaboration;
- analytics;
- automation;
- integrations;
- premium templates/assets;
- organizational capabilities;
- higher AI usage.

Pricing and tier limits remain intentionally open until usage and infrastructure costs are understood.

## What we are not building yet

- an open-ended metaverse;
- avatar walking mechanics as a core interaction;
- a generic 3D game;
- a marketplace before creator supply exists;
- enterprise digital twins before the public interaction model is validated;
- arbitrary industry worlds without evidence of demand;
- static AI-generated images pretending to be the interactive world.
